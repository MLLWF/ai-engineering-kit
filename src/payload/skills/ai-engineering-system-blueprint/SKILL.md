# AI 工程系统蓝图

在 AI 工程协议的架构阶段使用此技能。系统蓝图是**以图为主的宏观架构文档**——人类通过图快速理解 AI 后续工作的整体系统规划是否合理，AI 据此识别模块边界、依赖顺序、可并行工作和不可偏离的交互关系。

## 前置条件

背景事实分区和重大决策事实分区必须已经处于拍板状态，否则提醒用户先使用 `ai-engineering-consensus` 完成共识。满足前置条件后，可以按需参考其他事实分区、已有文档和代码库。

## 核心设计原则

1. **以图为主，文字极简**：`architecture.md` 的主体是图。文字仅用于：① 图表无法自解释的结论；② 一句话说明构图依据。**严格禁止**将背景描述、决策理由、实现细节、问题列表写入 architecture.md——这些必须留在 `background.md`、`decisions.md`、`questions.md`。
2. **四张图各司其职，不冗余**：每张图有明确的、不重叠的职责。画每张图之前，先确认"这张图要回答的问题是什么，其他图不回答它"。
3. **描述架构，不描述实现**：表达模块职责、边界、依赖和关键交互；不表达类名、函数名、文件路径、测试用例、任务状态或代码开发步骤。
4. **迭代至审批**：系统蓝图必须迭代到人类明确审批；审批前不得作为计划拆解和实现依据。

## 四张图的整体分工

在画任何图之前，先理解四张图的关系——它们形成"外→内→静→动"的阅读链路：

```
系统边界图          核心结构图          模块协作图          关键链路图
(外—谁在外面)  →  (内—怎么分层)  →  (静—谁和谁有接口)  →  (动—一个场景怎么走)
   宏观               中观               微观                 纵向
```

| 图 | 视角 | 回答的问题 | 粒度 | 唯一职责 |
|---|---|---|---|---|
| 系统边界图 | 外部视角 | 系统是什么？谁用？依赖谁？ | 系统级 + 外部角色 | 定义系统边界和外部交互 |
| 核心结构图 | 内部组织 | 内部怎么分层？每层职责？依赖方向？ | 层 + 模块 | 定义分层骨架和模块归属 |
| 模块协作图 | 接口契约 | 哪两个模块之间有接口？传什么？不能怎样？ | 模块对（成对） | 定义模块间接口约束 |
| 关键链路图 | 场景穿越 | 某个具体场景下，数据/命令如何端到端穿过系统？ | 模块序列（链式） | 验证结构和协作在一组具体场景下走得通 |

**核心约束：四种图之间不得出现内容重叠。** 如果发现同一段连线/路径出现在两种图中，说明职责混淆，必须去掉一个。

## 工作流

1. 先读 `docs/project/index.md`，沿路由进入相关事实分区。不加载无关分区。
2. 阅读代码或已有文档，获取事实依据。
3. **先完成核心结构图的分层推演**（这是所有后续图的基础），再依次产出其他三张图。
4. 产出每张图之后，对照"四种图的整体分工"表检查是否与其他图重叠。
5. 写入 `docs/project/architecture.md` 的 `待拍板` 区块，问人类："哪里不对、缺失、过度耦合或画错了？"
6. 每条反馈修改后，执行三种自检：**单图自检**（见下文）+ **交叉冗余检查**（见下文）+ **结构一致性检查**（见下文）。
7. 重复"产出 → 调整 → 产出"直到人类显式审批。
8. 审批通过后，按 `docs/ai-engineering/fact-record-spec.md` 写回 `architecture.md`，只保留已拍板章节。

## 一、系统边界图

### 这张图回答什么问题（唯一职责）

"核心系统是什么？谁/什么在使用它？它依赖哪些外部系统？边界在哪里？"

**不回答**：内部结构、模块接口、运行时路径。（那些是后面三张图的事。）

### 构图方法论

1. **先列清单**：外部角色（人、客户端、设备、服务）→ 核心系统对外能力（顶层，不展开内部）→ 外部依赖资源（硬件、第三方服务、外部存储）。
2. **画图**：用 `subgraph` 明确分隔系统内/外。外部系统和角色保持黑盒，核心系统内部只展示顶层能力域。
3. **箭头**：每条箭头标注交互内容和协议（如 `P2P 视频流`，不写"调用"）。
4. **节点总数 6-15 个**。

**什么算"系统内"？** 代码由本工程构建/部署的，就是系统内。反之是系统外。

### 常见错误

| 错误 | 正确做法 |
|---|---|
| 外部系统展开了内部结构 | 外部系统永远是黑盒 |
| 系统内展开了子模块 | 子模块留给核心结构图 |
| 箭头标注无内容（只写"调用"） | 标注交互数据/命令和协议 |
| 边界模糊（内/外没有 visual 分隔） | 必须用 subgraph 分隔 |

### 构图自检（全部满足才通过）

- [ ] subgraph 是否视觉上明确分隔系统内/外？
- [ ] 每条箭头是否标注了交互内容/协议？
- [ ] 外部系统是否都是黑盒（无展开内部）？
- [ ] 节点总数 ≤ 15？

## 二、核心结构图

### 这张图回答什么问题（唯一职责）

"核心系统内部如何分层？每层职责是什么？层间依赖方向是什么？AI 实现时代码应该放在哪一层？"

**这是最重要的图**——它是 AI 后续实现的宏观骨架，直接决定模块边界和耦合方向。

**不回答**：模块间的具体接口契约（留给协作图）、端到端运行时路径（留给链路图）。

### 构图方法论：分层职责推演法

**画图之前必须完成以下 4 步推演，推演结论写入 `结构结论`。**

#### Step 1 — 识别能力域

从系统边界图出发，列出核心系统必须提供的"能力域"（能力方向，不是具体模块）。数量通常 3-7 个。命名：`Xxx 能力`。

#### Step 2 — 按"抽象层级"和"变化频率"分层

将能力域归入 **3-5 个层次**。两个分层维度：

- **抽象层级**：越往上越贴近业务，越往下越贴近底层技术
- **变化频率**：越往上变化越频繁，越往下越稳定

**分层是通用方法论，层次命名和数量因系统类型而异**。参考模式：

| 系统类型 | 典型分层（从上到下） |
|---|---|
| 嵌入式/物联网设备 | 应用编排 → 业务服务 → 设备抽象 → 平台适配 → 基础能力 |
| Web 后端服务 | 接口层 → 应用服务 → 领域核心 → 基础设施 |
| CLI/桌面工具 | 交互层 → 功能核心 → 数据适配 → 外部集成 |
| 数据处理管道 | 接入层 → 处理编排 → 计算引擎 → 存储适配 |

某层只有一个模块且未来不太可能拆分时，与相邻层合并。简单系统 3 层，复杂系统不超过 5 层。

#### Step 3 — 定义每层职责和依赖方向

为每层写**一句话职责定义**，确定依赖方向：

- **只能上层依赖下层**。依赖方向 = 编译依赖方向。
- **同层可协作但不耦合**：同层模块通过接口/事件协作，不直接依赖对方内部。
- **禁止反向依赖**：下层不能依赖上层。
- **禁止跨层调用**：第 N 层只能调第 N+1 层。跨层说明中间层缺失抽象。

#### Step 4 — 画出嵌套层次图

每层一个 `subgraph`，标签 `层次名 — 一句话职责`，内部列出该层关键模块（每层 2-5 个）。层次 TB 方向从上到下排列，不同层不同填充色。节点总数 8-20。

### 常见错误

| 错误 | 正确做法 |
|---|---|
| 跳过推演直接画图 | 必须完成 Step 1-3，结论写入结构结论 |
| 所有模块平铺一层 | 分层是结构图的核心价值 |
| 层间反向依赖 | 依赖只能从上向下 |
| 同层模块全连接 | 全连接说明该层需要拆分 |
| 展开函数/类级细节 | 结构图只到模块级 |

### 构图自检

- [ ] 是否完成了 Step 1-3 推演并写入结构结论？
- [ ] 是否存在 3-5 个清晰层次，每层职责互不重叠？
- [ ] 所有依赖箭头是否从上向下（无反向、无跨层）？
- [ ] 每层是否都有"一句话职责"标签？

## 三、模块协作图

### 这张图回答什么问题（唯一职责）

"哪两个模块之间有接口？接口传什么？方向怎样？不允许怎样的耦合？AI 实现时应该在哪里定义接口、遵循什么约束？"

**这是接口契约图**——只画成对的模块接口关系，不画端到端路径。

**不回答**：分层骨架（结构图已回答）、端到端场景路径（链路图回答）。

### 关键区分：接口 vs 路径

| | 模块协作图（本图） | 关键链路图 |
|---|---|---|
| 画什么 | **成对的接口关系**（A↔B、B↔C、C↔D） | **链式的端到端路径**（A→B→C→D 完整穿越） |
| 视角 | 静态结构——"系统有哪些接口" | 动态行为——"场景 X 怎么走完" |
| 一个节点出现几次 | 可能在多对接口中出现 | 在一条路径中出现一次 |
| 类比 | 电路图——元件之间的连接点 | 信号追踪——一个信号从输入到输出的完整路径 |

**如果协作图画了"数据从 A→B→C→D"的完整路径，它就侵入了链路图的职责。协作图只画"A↔B 有接口"，"B↔C 有接口"，各自独立。**

### 构图方法论

1. **只画成对的接口关系**：每一对 = 两个模块之间的一组交互。可以多条线（同步命令 + 异步事件 + 数据推送），但都属于"A↔B"这个接口对。
2. **协作图 ≠ 路线图**：不要串联模块形成路径。如果你的图看起来像一条线从入口穿到出口，那你画的是链路图，不是协作图。
3. **标注每条接口线**：方向 + 同步/异步 + 交互方式 + 传了什么。
4. **协作契约表是核心产出**——比图更重要：

| 接口对 | 方向 | 传什么 | 交互方式 | 不允许的耦合 |
|---|---|---|---|---|
| A → B | 单向 | 启动/停止命令 | 同步调用 | B 不能反向调 A；A 不访问 B 内部 |
| C ↔ D | 双向 | 帧数据 → / 消费确认 ← | 有界队列 | 消费者不持有生产者指针 |

5. 节点数 8-15，聚焦中间 2-3 层的模块协作。基础设施层只做简单依赖，不展开。

### 常见错误

| 错误 | 正确做法 |
|---|---|
| 把协作图画成了端到端路径（入口→A→B→C→出口） | 协作图只画接口对，路径留给链路图 |
| 协作图的内容和关键链路图重复 | 马上检查：协作图里有完整路径吗？有就删掉 |
| 交互线无标注 | 每条线标方向+同步/异步+传什么 |
| 没有"不允许的耦合"列 | 这是审批关键，必须列出 |

### 构图自检

- [ ] 图中是否只包含成对的接口关系（没有串联成端到端路径）？
- [ ] **交叉检查**：和关键链路图对比——有没有同一段连线出现在两张图中？
- [ ] 每条接口线是否标注了方向和交互方式？
- [ ] 协作契约表是否包含"不允许的耦合"列？
- [ ] 是否没有全连接（每个模块接口对 ≤ 4）？

## 四、关键链路图

### 这张图回答什么问题（唯一职责）

"在某个具体场景下，数据/命令从进入系统到离开系统，完整穿过了哪些模块？每个模块在这一步做了什么？"

**这是场景验证图**——穿起协作图中已定义的接口，验证在具体场景下整个系统走得通。

**不回答**：模块间的接口定义（协作图已回答）、分层骨架（结构图已回答）。

### 与协作图的关系

协作图定义了"A↔B 有接口，传 X"。链路图说"场景 S 下，命令从入口→A→B→C→响应出口，其中 A→B 用了协作图中定义的 X 接口"。**链路图复述协作图的接口，不重新定义接口。**

### 构图方法论

1. **只选最关键的端到端场景，1-2 个**。判断标准：覆盖系统核心功能 + 跨层最多 + 代表了不同类型的流。
   - 通常：一条数据流链路（数据从哪进、经过什么处理、从哪出）+ 一条控制流链路（命令从哪进、经过哪些模块、响应从哪出）。
   - 如果系统只有一种流类型，只需一条。
2. **链路图上的每个节点必须能在核心结构图中找到对应模块**。链路是结构图上已有模块的"串行化"。
3. **图类型按链路性质选**：数据流/处理流程 → `graph LR`；跨模块时序交互 → `sequenceDiagram`；状态变迁 → `stateDiagram`。
4. **粒度对齐结构图**：链路节点粒度 = 结构图模块粒度，不展开到函数/类。

### 常见错误

| 错误 | 正确做法 |
|---|---|
| 链路图中的接口细节重新定义了一遍（和协作图重复） | 链路图只画模块穿越顺序，接口不重新描述 |
| 数据链路和控制链路内容与协作图的"数据面""控制面"重叠 | 删除协作图中任何"完整路径"式的内容 |
| 画了 3 条以上链路 | 只选 1-2 条最关键的 |
| 链路图节点在结构图中找不到 | 必须一一对应 |

### 构图自检

- [ ] 是否只选了 1-2 条端到端场景（不是 3+ 条）？
- [ ] **交叉检查**：链路图内容是否和协作图重叠？如有，删协作图中的路径、保留链路图。
- [ ] 链路图每个节点是否在结构图中可找到？
- [ ] 是否没有重新定义接口（只引用了协作图中已定义的接口）？

## 交叉冗余检查（画完所有图后必须执行）

在提交给人类审批之前，逐对检查四种图之间是否存在内容重叠：

| 检查对 | 如果出现以下情况，说明冗余 | 修复方式 |
|---|---|---|
| 结构图 vs 协作图 | 协作图重新画了层间依赖箭头 | 层间依赖只在结构图中表达，协作图不画 |
| **协作图 vs 链路图** | 同一段连线（如 A→B→C）在两张图中都出现 | **删协作图中的路径链，只保留成对接口；链路图保留完整路径** |
| 边界图 vs 链路图 | 边界图的外部箭头和链路图的首尾段重复 | 链路图的首尾节点用结构图模块，不重复画外部角色 |
| 结构图 vs 链路图 | 链路图中的模块不在结构图分层中 | 要么补到结构图，要么从链路图删除 |

## 结构一致性检查（画完所有图后必须执行）

- [ ] 边界图的核心系统顶层能力域，是否在结构图的某个层或模块中能找到对应实现？
- [ ] 协作图中的每个模块，是否都在结构图的某个层中？
- [ ] 链路图中的每个节点，是否都在结构图和协作图中出现过？
- [ ] 结构图、协作图、链路图中的同一模块命名是否一致？

## 文字纪律

architecture.md 中的文字必须满足**全部**条件：

1. 图表无法自解释——只看图会误解或遗漏关键信息
2. 每条结论一句话，不写段落
3. 不重复图表已表达的信息
4. 不包含：背景描述、历史原因、决策过程、问题列表、实现建议、任务规划

**对照检查**（写完每条文字后自问）：

| 图已经表达了？ | 能 → 删 |
| 属于 background/decisions/questions？ | 属于 → 移走 |
| 超过一行？ | 超过 → 精简 |

## 质量标准

- **人类**读完后：能从上到下理解核心系统分层、模块接口契约和关键运行时链路，能判断架构是否合理
- **AI**读完后：能识别模块边界、依赖顺序、可并行工作、不可偏离的交互关系，能在不额外澄清架构方向的情况下开始实现
